# 备份恢复演练可复跑化（P4-4）

## 问题

部署手册把 `pg_dump -Fc` + `pg_restore --exit-on-error` + 恢复库对比列为已验证项，但那是 `0001`
时点人工做过一次的结果；此后新增 `0002`–`0005` 四支迁移，**没有证据表明现在的备份仍然可用**。
而且「命令跑通」不等于「备份可用」——真正要证明的是恢复出来的库在结构、行数、内容上都与源库一致。

## 做法

新增 `deploy/verify_backup_restore.sh`：转储 → 恢复到新库 → 对比 → 清理（`trap` 保证成败都清理），
`pg_restore --exit-on-error` 使任何一条语句失败都能让演练失败，而不是"尽力恢复"。

对比分为四层：

1. 迁移版本、表数量、检查约束数量、索引数量（结构）；
2. 逐表行数（数据量）；
3. 逐表内容摘要：`md5(string_agg(行文本 ORDER BY 行文本))`，覆盖所有列；
4. 恢复库与转储文件清理。

第 3 层是为了 JSON 列：行数相同但 JSON 被改坏，同样是"恢复成功"的假象。

## 结果

在 head = `0005`、含种子数据的库上实测，并额外插入一行带 JSON 的 `session_record`
（含中文值）与一行带 JSON 数组的 `media_asset` 以真正走到 JSON 往返：

| 项 | 结果 |
| --- | --- |
| `pg_dump -Fc` | 53,730 字节 |
| `pg_restore --exit-on-error` | 通过 |
| 结构 | `alembic_version=0005`、19 表、6 检查约束、54 索引，两侧一致 |
| 行数 | 19 张表全部一致 |
| 内容摘要 | 全部一致（含两张 JSON 表） |

**敏感性验证**（证明这个比较会失败，不是永远 PASS）：改 `session_record.completion_count`
一个字段，摘要 `5b54ede2…` → `d50b9cdd…`；改回后复原，且与演练中恢复库的摘要一致。

## 落选方案

- **只用行数对比**：JSON 内容损坏、字段错位都发现不了，而这正是最需要防的一类。故加内容摘要。
- **写成 Python 脚本**（与 `verify.py`、`verify_postgres.py` 一致）：`pg_dump`/`pg_restore` 是外部
  二进制，Python 版要么依赖宿主机装了客户端，要么套一层 `docker exec`，而演练最自然的位置就是
  有客户端的地方。故用 bash，README 给出容器内与宿主机两种调用方式。
- **让脚本自己起临时库并塞满数据**：会让它同时承担"造数据"与"验数据"，失败时说不清是谁的问题。
  演练数据由调用方准备。

## 局限

- 演练应在停止写入时执行；数据量大时内容摘要要对整表排序，会较慢（演练库通常很小）。
- 只验证「转储→恢复」这一条路径；未做时间点恢复（PITR）、未接入云上对象存储与异地副本。
- 未做定期自动演练（需要调度与告警，属 P4-4 剩余部分）。
