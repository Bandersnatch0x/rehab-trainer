# 连接池上限与过载行为（P4-5 发现）

## 现象

`scripts/loadtest-api.py` 对单实例 API 压测（Windows Python 3.13 + 单进程 uvicorn，PostgreSQL 17.11）：

| 并发 | RPS | p50 | 结果 |
| --- | --- | --- | --- |
| 8 | 111 | 59–79 ms | 正常 |
| 16 | 144 | 96–118 ms | 正常 |
| 32 | 133 | 218–251 ms | 吞吐不再增长，延迟翻倍 |
| 64 | 1.6 | 约 29 s | 客户端 30 s 超时，服务近乎停摆 |

## 根因

`app/core/database.py` 用 `create_engine(url)` 未显式配置连接池，取 SQLAlchemy 默认值
`pool_size=5`、`max_overflow=10`，即**最多 15 个并发数据库连接**，`pool_timeout` 默认 30 秒。

证据：并发 40 时持续采样 `pg_stat_activity`，目标库后端连接数稳定停在 15，压测结束回落到 5。
并发 64 时 p50 恰为 29 秒，正是请求在池外排队到 `pool_timeout` 后失败的表现。

因此上限约 140 RPS ≈ 15 连接 × 1/0.105 s，且**过载不降级而是挂起**：客户端要等 30 秒才拿到错误，
期间连接与线程都被占用。

## 待决策

1. **池大小**：按部署形态显式配置（副本数 × 池大小必须低于 PostgreSQL `max_connections` 并留余量），
   并评估是否需要调大 PostgreSQL 侧 `max_connections`。属部署参数，需与 P4-1 一起定。
2. **过载反馈**：把「排队到 30 秒再失败」改为快速失败。这要给契约补一个 5xx 响应
   （现有契约只声明 200/201/401/403/404/409/422/429），属契约变更，需先决定错误码与状态码，
   再改 openapi、生成物与客户端错误处理。

## 本次未做

未改动任何运行时行为：只测量并记录。凭据仍缺，未在真实多副本或生产规格机器上验证。

### 2026-11-07 压测中发现的第二个同源问题：连接池不探活

现象：数据库容器重启（等价于生产里的数据库重启/主从切换）后，API 未重启的情况下继续返回
HTTP 500，或在客户端侧表现为挂起。服务端日志为：

```
sqlalchemy.exc.OperationalError: (psycopg.OperationalError) consuming input failed:
could not receive data from server: Software caused connection abort (0x00002745/10053)
[SQL: SELECT count(*) FROM login_failure WHERE username = ...]
```

根因与上面同出一处：`create_engine()` 未启用 `pool_pre_ping`，池里被对端关闭的连接会被原样取出使用，
第一次读写在死连接上失败并抛到路由层，直接变成 500；重试一次即可恢复，但当前没有重试与错误映射。

建议（与上面两项一起决策）：`pool_pre_ping=True`（代价是每次取连接多一次轻量往返），
并把「连接层瞬时故障」与「业务错误」区分开——前者可重试一次，后者不可。
这同样牵涉到把什么样的状态码交给客户端，与上面第 2 项是同一个契约决定。

### 2026-11-07 实施与验证

用户指示"做 0026"，两项决策按下列取值落地：

1. **池大小显式化、环境变量可调**（默认值维持原状，避免上线即改行为）：
   `REHAB_DB_POOL_SIZE=5`、`REHAB_DB_MAX_OVERFLOW=10`、`REHAB_DB_POOL_TIMEOUT_SECONDS=5`（原默认 30）、
   `REHAB_DB_POOL_PRE_PING=true`、`REHAB_DB_POOL_RECYCLE_SECONDS=1800`。SQLite 分支不动。
2. **过载与连接层故障都走 503**：`{"code":"SERVICE_UNAVAILABLE","detail":{"retryable":true}}`，
   错误原文只进日志。**未加自动请求重试**——`POST /patients` 之类非幂等端点若被中间件重试会重复写入；
   重试交给客户端，用 `retryable` 标记与 `Retry-After` 语义提示。
3. **契约**：新增 `components.responses.ServiceUnavailable`，25 个 operation 全部声明 `503`。

验证（同一 Windows 11 / 20 核 / PostgreSQL 17.11 / 单进程 uvicorn 环境）：

| 并发 | 修复前 | 修复后 |
| --- | --- | --- |
| 8 | 111 RPS，p50 59–79 ms | 102 RPS，p50 59–78 ms |
| 32 | 133 RPS，p50 218–251 ms | 84 RPS，p50 309–370 ms |
| 64 | 1.6 RPS，p50 约 29 s，近乎停摆 | 73 RPS，p99 ≤ 5.0 s，20 次快速 503 |

- 线上形态：1 条连接的池 + 200 并发 → 165 个 401 + **35 个 503**，响应体为上述契约形状；
  35 次失败对应 35 行 `连接池等待超时` 错误日志。
- 该实验同时证明环境变量真的生效（池被压到 1 条连接，行为随之改变）。
- 探活：数据库被整实例替换后，未重启的 API 下一个请求仍返回 200（257 ms）。
  这一步只证明"恢复可用"，未单独隔离 `pool_pre_ping` 的贡献，因此不把它当作探活的独立证据。
- 后端 pytest 120 → 127 项（新增 7 项：池参数来源、SQLite 不配池、`create_engine` 接受参数、
  两种异常都映射 503、响应不泄漏连接串/池内部信息、业务 401 不被误映射为 503）。

### 关闭说明

高并发吞吐低于修复前是**有意的取舍**：原先靠让调用方排队 30 秒换来一点吞吐，代价是分不清"慢"与"死"。
现在最坏等待被钉在 `pool_timeout`，超出立即返回可重试的 503。

仍未做，留给 P4-1/P4-5：

- 多副本下的池总量核算（需确定副本数与数据库 `max_connections`）。
- 客户端对 503 的统一退避重试；Android 训练记录已有本地队列重试，其余读取路径目前只提示失败。

### 2026-11-07 补：建连本身没有上界

真库验证就绪探针时发现：停掉数据库后 `/readyz` 挂了 15 秒以上没返回。
`pool_timeout` 只约束「排队等池」，**不约束建立连接**；对端停服但端口仍被转发时，
连接会一直等到操作系统放弃（Windows 约 20 秒）。

已加 `REHAB_DB_CONNECT_TIMEOUT_SECONDS`（默认 5，传给驱动的 `connect_timeout`）。
修复后同一场景 5.1 秒返回 503。细节见票 0032 的「真库验证」一节。

教训：这个票修的是「池排队无界」，但「建连无界」是另一个洞——同一个故障场景（数据库不可用）
有两段独立的等待，只堵住一段。

### 2026-11-07 复测（WSLC + PostgreSQL 16）

换到 WSLC 容器（本机 127.0.0.1 直连，不再经 WSL relay）重跑同一压测脚本，确认交付配置的形状：

| 并发 | RPS | p50 | p99 | 错误 |
| --- | --- | --- | --- | --- |
| 8 | 142.4 | 46–63 ms | 72–92 ms | 0 |
| 32 | 122.3 | 231–262 ms | 359–410 ms | 0 |
| 64 | 61.8 | 450–476 ms | 853–1007 ms | 6 次快速 503（登录），最大延迟 4.5 s |

并发上去后吞吐不再增长、延迟被钉在超时值附近、超出的请求立刻拿到可重试 503——与设计一致。
绝对 RPS 与首测不可比（PostgreSQL 16 vs 17、链路不同），可比的是形状。
